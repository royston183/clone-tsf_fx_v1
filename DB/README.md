# DB

The application's own SQLite database, for local work. SAP stays the system of record.

- `schema/NNNN_<name>.sql`: numbered migrations, the source of truth for every table. Add a new file for each
  change; never edit one that has been applied. Plain SQL types only, so the schema also runs on another database
  when the application moves to a server.
- `seed/*.sql`: optional starting data, run by `npm run build-db -- --seed`.
- `app.db`: built from `schema/` by `npm run build-db` (the BackEnd also applies new migrations when it starts).
  Git-ignored.

Tables:

- `app_modules`: the `app` modules already seeded with their sample data (0003_app_modules), so a module whose rows
  were all deleted is not seeded again.
- `layouts`: ALV layouts of modules with a data source, shared and personal.
- `schema_migrations`: kept by the migration runner.
- One generated table per table of each `app` module, named `<module>__<table>` (for example
  `sample_deals__deals`), with a column per field of its definition.

0001_init created `mock_store` (one JSON document per module), 0002_app_store renamed it to `app_store`, and
0004_drop_app_store dropped it: the module tables above replace it.

## Generated migrations

`npm run gen-schema` writes the module tables from the module definitions (`source: 'app'` in
`FrontEnd/src/modules/server-registry.ts`) into one migration, `NNNN_app_tables_<hash>.sql`, whose first line is
`-- generated by gen-schema`. `npm run dev` runs it before the BackEnd starts; FS Sprint runs it after every turn
that changed the application.

- **Pending**: a generated migration the Git remote does not have yet. Each run replaces it with one file holding the
  whole difference, and rebuilds the module tables of `app.db` that came from it.
- **Frozen**: one the Git remote has on any branch, and the template's own 0001–0004. It is never changed again; a
  later change goes into a new pending migration. A frozen column or table is never dropped, narrowed, widened or
  re-keyed: a definition that would need it is reported, and verify fails until the definition is restored or a new
  field is added.
- **Teammates**: the file name ends in the start of the SQL's hash, so two teammates who generate the same number get
  two files and Git merges both (the same SQL gets the same name and merges cleanly). Generated `CREATE TABLE` and
  `CREATE INDEX` use `IF NOT EXISTS`, so a fresh database runs both even when they create the same table; the next run
  adds whatever still differs. After Merge team changes brings in a pushed migration with your pending one's number,
  the next run (testing the app is enough) renames yours to the next number and keeps its tables and local data.
- `npm run verify` runs `npm run gen-schema -- --check`, which writes nothing and fails when `schema/` is behind the
  definitions or a frozen definition changed. It prints `Schema: up to date.` when nothing is to do.

**Never edit a generated migration**, and never write SQL for module tables by hand: change the module definition and
run `npm run gen-schema`. Gallery samples (`devOnly`) never get a migration: the local BackEnd creates their tables
when it starts, and the deployed (MySQL) BackEnd does not keep them.
